# The tools, and what to run when

Moved here as they stood from CLAUDE.md (2026-11-23, the user's "Yes, all five"). A new tool's or check's entry goes here. CLAUDE.md keeps the short rule of what to run for each version, before a merge and before a push.

## Tools (`research/tools/`, paths in `env.sh`; work files in `build/tools/`)
- `verify.sh [--full] [rev]`: the standard validation, one line each — firmware checks
  vs baseline, A/B renders vs `rev` (default HEAD), plugin build, PluginTest, the same through the chip,
  the effects' panel, the editor's layout, Auto's classifier (`classifier_test`), auval (v461: the instrument's AU and the effect build's, `auval aumu`, `auval aumf`). Run it for every version; `--full` before a push. Every line
  fails the run when its program fails. `verify_test.sh` (when verify.sh changes; it runs it whole): a stub auval that fails must fail the run, each AU's line (`auval aumu`, `auval aumf`, v461) saying so.
- `fcheck.sh [--update] [--full]`: every firmware harness on fixed cases against
  `fcheck_baseline.txt`, side by side. In a worktree set `PY` to the main checkout's `.venv/bin/python3`. A section is reused when its binary, command,
  ROM, disk image, inputs and the files it reads besides (`FILES=` before its `part` line: xtrecs.py, a project's waves) are those of a run that matched the baseline (`build/tools/fcheck/kept`
  in the main checkout, shared by the worktrees); `--full` runs them all. A new section that reads a script or data names it in `FILES`. `fcheck_keys_test.sh` (when fcheck.sh, build.sh, env.sh or a file build.sh takes from research/tools changes, a few minutes; it ran last at v171 and stopped at v174's include until v179): a changed xtrecs.py and a changed wave must run again. `--update`
  only when adding checks/cases on purpose, and read its diff: in a worktree with no `analysis/projects` link it runs without the project's waves and quietly loses their 28 lines.
- `ab.sh [rev]`: XtSynth CLI renders, `rev` vs working tree; `XT_*` env vars
  set controls (see the `XT_SYNTH_MAIN` comment in XtSynth.cpp).
- `pt.sh [note]`: PluginTest (processor vs XtSynth); `TEST_*` env vars (see
  `plugin/Tests/PluginTest.cpp`); `TEST_FX=1` runs both through the chip, with `TEST_FX_KNOBS`, `TEST_FX_EDIT`, `TEST_FX_LIVE`, `TEST_BUS`, and each effect parameter's name, range and default against its ID. `TEST_FX_PANEL=1` walks the panel's pages, with what each box says against the firmware's routine (VSynthEmuTest alone: it stops there); `TEST_SNAPSHOT_FX=page` draws one. `TEST_SNAPSHOT=file.png` draws the editor, D, as it opens, `TEST_SNAPSHOT_PAGE=n` on a page, `TEST_SNAPSHOT_BLOCK=n` with a block selected, `TEST_SNAPSHOT_SIZE=WxH` at that size (the editor's checks are `VSynthEmuEditorTest`'s, below, `TEST_UI_LAYOUT`'s until v196). `TEST_ROM_SEARCH=1` checks where a new instance finds the firmware image and what's kept (the same). PluginTest sets `VSE_APP_DIR` to a temporary folder for every run, so no test reads or writes the user's settings.

An encode is an `EncodeJob` (`addEncode`, `PluginEncodes.cpp`) whose firmware stops on the pool's exit signal through `Sh4StopScope`; a call with none held runs as before.
